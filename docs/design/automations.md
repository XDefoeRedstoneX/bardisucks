# Design: scenes & automation engine

> Status: proposal v0.1. This part is the whole reason the project exists, so it gets its own spec.
> Context: [architecture.md](architecture.md) · [research](../research/tuya-platform.md)

## 1. What we're fixing

| Tuya / BARDI scenes | This engine |
|---|---|
| Runs in Tuya's cloud, so no internet means no automations, plus a round trip overseas | Runs on the hub, works offline, ~100 ms reaction |
| Fixed menu of conditions | Any device capability, time windows, sun position, modes, AND/OR/NOT |
| No branching | `if/then/else`, `choose`, `repeat`, `wait_for` with timeout |
| Basic delays | delays, random delays, "for N minutes" triggers, software fades |
| A device can't be both trigger and action | allowed (with loop protection) |
| No memory | **modes** (home/away/sleep/…) and scene **snapshots** (restore what was on before) |
| No "why didn't it run?" | full **trace** for every run: trigger → each condition's result → each action |
| Phone-only UI | UI builder **and** YAML, export/import, webhooks for Shortcuts/Tasker/NFC |

## 2. Concepts

```
Automation = triggers (ANY fires) → conditions (ALL must pass) → actions (sequence)
Scene      = { device: target state } applied in parallel
Mode       = one global value, e.g. home | away | sleep | movie (user-defined list)
Snapshot   = saved copy of some devices' current state, restored later
```

The **run mode** decides what happens when an automation triggers while it's still running (e.g. during a `delay`):

| Run mode | Behaviour | Typical use |
|---|---|---|
| `single` (default) | ignore the new trigger | one-shot actions |
| `restart` | cancel the running instance, start again | motion/"keep on while busy"-style timers |
| `queued` | run after the current one finishes (max 10) | sequential stuff |
| `parallel` | run alongside it | independent notifications |

## 3. Schema

Automations are stored as JSON in SQLite. The UI edits them through forms, and power users can edit the same thing as YAML. Durations are written `30s`, `15m`, `2h`, `1h30m`. Times are `HH:MM` in the hub's timezone (default `Asia/Jakarta`).

### 3.1 Triggers

| Type | Fields | Fires when |
|---|---|---|
| `time` | `at: "06:30"` · `weekdays: [mon..sun]` | clock hits the time |
| `cron` | `cron: "*/15 18-23 * * *"` | power-user schedule |
| `sun` | `event: sunrise\|sunset\|dawn\|dusk` · `offset: -15m` | sun event at the configured location |
| `device` | `device` · `capability` · `to` / `from` / `above` / `below` · `for: 2m` | state changes (and stays that way for `for`) |
| `device_event` | `device` · `event: online\|offline\|command_failed` | connectivity events (e.g. back after a power cut) |
| `mode` | `to` / `from` | mode changes |
| `webhook` | `id` (secret generated by the hub) | `POST /api/hooks/{id}`, from Shortcuts, Tasker, NFC tags, other systems |
| `manual` | none | Run button in the app, or `automation.run` from another automation |
| `hub` | `event: start` | hub boots (good for "restore after outage") |

Every trigger can carry an `id` so actions can branch on *which* trigger fired (`trigger.id`).

### 3.2 Conditions

| Type | Fields |
|---|---|
| `time` | `after` · `before` (may wrap midnight) · `weekdays` |
| `sun` | `after: sunset` · `before: sunrise` (+ offsets). "Is it dark?" |
| `device` | `device` · `capability` · `is` / `is_not` / `above` / `below` · optional `for` |
| `online` | `device` · `is: true\|false` |
| `mode` | `is` / `is_not` (single value or list) |
| `trigger` | `id` — which trigger started this run |
| `and` / `or` / `not` | `conditions: [...]` |

### 3.3 Actions

| Action | Example |
|---|---|
| `set` | `set: { device: lamp-living, power: true, brightness: 30, color_temp: 20, transition: 10m }` |
| `toggle` | `toggle: lamp-living` |
| `scene` | `scene: warm-evening` (optional `transition`) |
| `snapshot` / `restore` | `snapshot: { name: before-movie, devices: [lamp-living, lamp-bed] }` → `restore: before-movie` |
| `delay` | `delay: 5m` · `delay: { random: [0m, 20m] }` |
| `wait_for` | `wait_for: { condition: {...}, timeout: 10m, on_timeout: continue\|stop }` |
| `if` | `if: [conditions] · then: [actions] · else: [actions]` |
| `choose` | list of `{ when: [conditions], do: [actions] }` + `default` |
| `repeat` | `repeat: { count: 3 \| while: [...] \| until: [...], do: [...] }` |
| `parallel` | `parallel: [[actions], [actions]]` |
| `mode` | `mode: sleep` |
| `notify` | `notify: { title: "…", message: "…", priority: high }` (ntfy) |
| `automation` | `automation: { run: other-id }` · `{ enable/disable: id }` |
| `stop` | `stop: "reason"` (shows up in the trace) |

Device targets can be a single id, a list, a `room: bedroom`, or `all: lights`.

## 4. Cookbook: things BARDI couldn't do

**1) Sunset lights, but only if someone's home**
```yaml
id: sunset-lights
name: Sunset → warm lights
triggers:
  - sun: { event: sunset, offset: -15m }
conditions:
  - mode: { is: home }
actions:
  - set: { device: [lamp-living, lamp-bed], power: true, brightness: 60, color_temp: 15, transition: 15m }
```
(Near the equator, sunset in Jakarta only moves between about 17:45 and 18:15 over the year, so a fixed time almost works. A sun trigger handles the drift for free, though.)

**2) Bedtime button: dim slowly, then off, then sleep mode**
```yaml
id: bedtime
name: Bedtime
mode: restart
triggers:
  - manual: {}
  - webhook: { id: auto-generated }   # NFC sticker on the nightstand
actions:
  - mode: sleep
  - set: { device: lamp-living, power: false }
  - set: { device: lamp-bed, brightness: 20, color_temp: 0, transition: 2m }
  - delay: 15m
  - set: { device: lamp-bed, brightness: 1, transition: 5m }
  - set: { device: lamp-bed, power: false }
```

**3) Wake-up light on weekdays (sunrise simulation)**
```yaml
id: wake-up
triggers:
  - time: { at: "05:30", weekdays: [mon, tue, wed, thu, fri] }
conditions:
  - mode: { is_not: away }
actions:
  - set: { device: lamp-bed, power: true, brightness: 1, color: { h: 20, s: 90 } }
  - set: { device: lamp-bed, brightness: 70, color_temp: 60, transition: 20m }
  - mode: home
```

**4) Movie mode from the TV's outlet power draw** (once you have a metering outlet)
```yaml
id: movie-auto
mode: restart
triggers:
  - { id: tv_on,  device: { device: plug-tv, capability: power_w, above: 40, for: 1m } }
  - { id: tv_off, device: { device: plug-tv, capability: power_w, below: 5,  for: 5m } }
conditions:
  - sun: { after: sunset, before: sunrise }
actions:
  - choose:
      - when: [ { trigger: { id: tv_on } } ]
        do:
          - snapshot: { name: pre-movie, devices: [lamp-living] }
          - scene: { id: movie, transition: 5s }
      - when: [ { trigger: { id: tv_off } } ]
        do:
          - restore: { name: pre-movie, transition: 5s }
```

**5) Safety: outlet on too long → turn off + notify**
```yaml
id: iron-guard
triggers:
  - device: { device: plug-iron, capability: power, to: true, for: 45m }
actions:
  - set: { device: plug-iron, power: false }
  - notify: { title: "Iron turned off", message: "It was on for 45 minutes.", priority: high }
```

**6) Away mode: lights that look lived-in**
```yaml
id: vacation-sim
triggers:
  - sun: { event: sunset, offset: 10m }
conditions:
  - mode: { is: away }
actions:
  - delay: { random: [0m, 30m] }
  - set: { device: lamp-living, power: true, brightness: 70 }
  - delay: { random: [2h, 3h30m] }
  - set: { device: lamp-living, power: false }
  - set: { device: lamp-bed, power: true, brightness: 40 }
  - delay: { random: [20m, 60m] }
  - set: { device: lamp-bed, power: false }
```

**7) After a power cut, put things back the way they were**
```yaml
id: restore-after-outage
mode: queued
triggers:
  - device_event: { device: [lamp-living, lamp-bed], event: online }
conditions:
  - mode: { is: home }
actions:
  - if: [ { sun: { after: sunset, before: "23:00" } } ]
    then: [ { scene: warm-evening } ]
    else: [ { set: { device: "{{ trigger.device }}", power: false } } ]
```

**8) One-tap toggle from the phone's home screen / quick-settings tile**
```yaml
id: toggle-living
triggers: [ { webhook: { id: auto-generated } } ]
actions: [ { toggle: lamp-living } ]
```

## 5. Engine internals

```
           ┌───────────── Event bus (asyncio) ─────────────┐
 Drivers ──► state_changed / online / offline / failed     │
 Scheduler ► time / cron / sun ticks                       │
 API ──────► webhook / manual / mode_changed               │
           └────────────────────────┬──────────────────────┘
                                    ▼
                       Trigger matcher (index by event type + device)
                                    ▼
                  Run manager (applies run mode, creates Run)
                                    ▼
             Run: evaluate conditions → execute actions step by step
                     │                    │
                     ▼                    ▼
               Trace recorder      Device registry (desired state,
               (SQLite, last 50     coalesced commands to drivers)
                runs/automation)
```

- **Scheduler:** keeps a min-heap of the next fire time for every `time`/`cron`/`sun` trigger. It recomputes after each fire, after edits, and at midnight (for sun times). It doesn't poll every second.
- **`for:` durations:** when a `device` trigger matches, the engine starts a timer. Any state change that breaks the match cancels it. When the timer finishes, the trigger fires. Same mechanism for `for:` in conditions.
- **Device state in conditions** reads the registry's *reported* state, not desired.
- **Delays survive nothing:** if the hub restarts mid-run, that run is marked `aborted` in the trace. Delays aren't persisted, which keeps things simple. Long waits should be separate time-triggered automations instead.
- **Catch-up:** each time/sun trigger has an optional `catch_up: 30m`. On hub start, triggers that were missed within that window fire once.
- **Loop protection:** a run started by a device change that the *same* automation caused gets ignored (tracked by a context id on commands, like HA's `context`). There's also a hard cap of 10 runs/minute per automation. Going over it auto-disables the automation and sends a notification.
- **Validation:** Pydantic models for every trigger, condition and action type. Saving an automation that references an unknown device, a capability the device lacks, or an out-of-range value gets rejected with a pointer to the bad field.
- **Templating (later):** a small, safe expression set (`trigger.device`, `trigger.id`, `state('plug-tv','power_w')`, `now()`), not full Jinja. Only needed for cookbook #7-style rules, so v1 can start without it.

## 6. Trace format

Every run stores something like:

```json
{
  "automation": "movie-auto",
  "run_id": "r_01J…",
  "started": "2026-11-02T19:41:07+07:00",
  "trigger": { "id": "tv_on", "type": "device", "device": "plug-tv", "value": 58.3 },
  "conditions": [ { "type": "sun", "result": true, "detail": "after sunset 17:52" } ],
  "steps": [
    { "path": "actions[0].choose[0]", "result": "taken" },
    { "path": "…snapshot", "result": "ok", "saved": ["lamp-living"] },
    { "path": "…scene", "result": "ok", "duration_ms": 412 }
  ],
  "finished": "2026-11-02T19:41:08+07:00",
  "status": "ok"
}
```

The app renders this as a timeline. Runs that were skipped because a condition failed also get logged (with the failing condition highlighted). That answers the "why didn't my automation run?" question that Tuya can't.

## 7. Build order (inside roadmap phase 4)

1. Event bus, run manager, `manual` trigger, `set`/`toggle`/`scene`/`delay` actions, traces
2. `time`, `sun` triggers + scheduler; `time`/`sun`/`mode`/`device` conditions
3. `device` triggers with `for:`; `if`/`choose`/`wait_for`; modes; snapshot/restore
4. Webhooks + notify; loop protection; catch-up
5. UI builder; YAML editor; trace viewer
6. Templating, `repeat`, `parallel`, random delays
